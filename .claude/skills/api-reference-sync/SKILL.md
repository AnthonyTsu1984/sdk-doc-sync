# API Reference Sync

Synchronize versioned API-reference records without changing established documentation ownership or release history.

## Trigger Boundary

Use for release-range discovery, API-reference inventory, versioned record planning, backfill, deprecation, reparenting, or source-backed SDK/CLI/REST reference updates.

Do not use for a narrative guide, localization, verification-only code checks, or missing language tabs in one procedure. Use `verified-doc-authoring`, `localized-doc-sync`, `doc-code-verify`, or `procedure-code-sync` respectively.

## Permission Boundary

- Discovery, source inspection, Feishu indexing, placement audit, planning, and dry-run are read-only.
- Do not write until the user reviews the complete dry-run and gives explicit approval for its exact batch digest.
- Live writes may touch only approved documents, records, folders, and metadata. Never write the auto-populated `Slug` field.
- Keep the older-version doc as a historical snapshot. Never patch or delete an inherited older-version document during a newer release sync.
- Write approval does not authorize Acceptance Finalization. Keep touched interface-document records `WIP` until separate acceptance changes them to `Draft` and advances `scan-state.json`. The executor never writes `Targets` on interface-document records — existing values are preserved verbatim and records created by the run start blank; the final `[Milvus, Zilliz]` unification is an operator step after finalization. Structural VirtualNode or Module records preserve existing publication metadata when repointed; new structural records use the explicit reviewed `Targets` and `Progress` values in their approved resource plans.
- A partial-acceptance request is blocked. Until every unit is accepted and the complete manifest digest is supplied, the next missing gate remains `APPROVE_ACCEPTANCE`; never report that no acceptance approval is required.
- Write or document acceptance does not authorize rollback. A single executed unit may be rolled back only before final acceptance, through its own deterministic manifest and exact `APPROVE_ROLLBACK <review-unit-id> sha256:<rollback-manifest-digest>` command. Rollback never advances or rewinds `scan-state.json`.

## Shared Contract

- Capability baseline: [capabilities.json](capabilities.json).
- Canonical artifacts, lineage, approval envelopes, journals, state transitions, and result semantics come from `../doc-ops-core/contracts/` and `../doc-ops-core/src/`.
- REST/OpenAPI review uses one unit per `(versionTrack, endpoint, method)`, not one unit per rendered document. Read `sdk-rest.md` and use the REST track manifest CLI; the generic Feishu document execution state machine does not apply to zdoc spec-file writes.
- REST fragment production is a local, deterministic operation. Data-plane collections come from pinned Milvus revisions; control-plane collections come from pinned zilliz-cloud base/head revisions and the explicit service allowlist. It must not read control-plane truth from Feishu or infer publication versions from OpenAPI `info.version` or `/v1`/`/v2` paths.
- REST source adapters may extract source routes, but they must never guess an internal-to-public control-plane mapping. When constants, gateways, request-shape transformations, split/combined operations, or missing controller ownership prevent an exact automatic mapping, follow the agent mapping investigation in `sdk-rest.md`. This is work for the agent, not a request for the user to confirm routes. Keep the service blocked until the agent records source-backed mapping evidence; path similarity alone is not approval.
- PR intake from `milvus-io/web-content` is read-only discovery (`bin/sdk-pr-scan.js`, see `sdk-pr-sync.md`). It pins the PR merge commit and the SDK target tag, verifies every page change against SDK source, and must emit a `validateReleaseScope`-passing artifact before the standard candidate pipeline runs. Only MERGED PRs are solidifiable; Feishu-local edits diverging from a PR surface at the grouping review gate and are decided page by page — intake never silently overwrites them. Languages without a track (csharp, rust) produce inventory-only artifacts (`NO_FEISHU_TRACK`). After a PR page's verbatim landing verifies, an optional post-verbatim polish phase runs inside the same unit before document review (`bin/pr-polish.js`, see `sdk-pr-sync.md`): a polish subagent proposes a manifest, deterministic gates validate and recompute the terminal bytes, and acceptance binds the polished terminal state.
- Full-scope planning emits a deterministic `reviewUnitManifest` with exactly one unit per public document. Do not approve or execute a multi-document release batch.
- The manifest digest binds the stable document sequence and inter-document prerequisites, not stale future write plans. Replan the selected unit against current live state immediately before approval; its separate batch digest binds the actual resource and document operations.
- Select one unit with `--review-unit-id <id>`, rerun its scoped dry-run, and approve only that unit's `proposedExecutionBatch.batchDigest` through `--approve-batch-digest <hash>`. A changed artifact, resource plan, comment-driven correction, or unit selection creates a new batch and requires new approval.
- After one unit executes and verifies, stop for `DOCUMENT_REVIEW`. Writes to the next unit require the user's acceptance of the active document — or, in verified batch mode, the batch gates defined below. Read-only preparation is always allowed: the next unit may be selected and planned with a scoped dry-run while the active document awaits review, and a plan produced that way is stale by approval time — replan against current live state immediately before any write approval. In the two-gate acceptance flow (2026-10-01 ruling) document acceptance IS the unit's final acceptance: the governed `WIP→Draft` transitions land with a digest-bound per-unit receipt and the unit finalizes (terminal — rollback and change requests refuse; corrective release instead); `scan-state.json` moves only when the session closes mechanically once every unit finalized (`close-session`, no approval gate). Legacy campaigns continue in place, never rebuilt: `sdk-review-session.js migrate-to-two-gate` finalizes every accepted unit (one operator gate, governed Draft writes, per-unit receipts) and flips the session's flow, and `transfer-unit-completion` marks a unit completed in another session accepted from that session's digest-bound receipt.
- Verified batch mode is an explicit operator decision per release, never a default. The operator sets the batch size `K` (the first batch of a release is a canary the operator observes end to end, and `K` stays small until a batch has passed review). One WRITE gate authorizes the ordered list of the next `K` manifest units as a batch: the approval binds the unit identity list and the batch rules, not per-unit digests. Under the two-gate ruling the APPROVE_WRITE presentation is batched too — fewer than 20 pending documents are one gate, 20 or more are presented in order in batches of 20 (`chunkWriteApprovalBatches`) — with each document's collected materials reachable by clickable file path. The workflow then, per unit in manifest order: replans that unit against current live state immediately before executing it, executes its exact batch, and runs the complete deterministic verification — journal completion sentinel, successful `api.versioned-tree-delta` outcome, content fidelity, layout conformance, and live record verification. Any verification failure stops the batch immediately; every already-verified unit stays intact and verified. Per-unit batch digests are journaled and reported in the batch review. One DOCUMENT_REVIEW gate then reviews the whole batch against the complete touched-inventory presentation (every unit's document and record links); in the two-gate flow approval finalizes each reviewed unit (`WIP→Draft` + per-unit receipt), and a change request names the specific units that revert to individual rebuild while the rest proceed. Every other invariant is unchanged: per-unit rollback stays available until a unit finalizes, and a new invariant failure inside any batch freezes batch mode for that release until root-caused.
- Persist collaborative progress in a review-session JSON file outside model context. Create it only from the complete initial dry-run with `--session-state`; every later process or chat must use `--resume-session`, which revalidates the original manifest, accepted execution journals, live `WIP` records, `Targets` unchanged from each unit's execution baseline (the journal's rollback capsule — the executor never writes `Targets`), and unchanged document tokens before planning the next unit. Never accept caller-declared review-unit IDs as proof of prior acceptance. Context rotation is a gate-boundary discipline: one campaign is one canonical session file and chats rotate within it (~42% context budget), a chat hands off only after the current gate's artifacts are durable on disk, and an approval not yet embodied in its durable artifact (execution journal, acceptance receipt, session transition) does not survive rotation — the fresh chat re-presents that gate, guided by the `nextGate` field of `sdk-review-session.js status`.
- If the user requests changes or leaves review comments, read all comments on the active document, rebuild only that unit's reviewed artifacts and resource plan, invalidate its old batch and journal digests, and return to scoped write approval. Never continue to the next unit while comments remain unresolved.
- Journal every approved action before and after mutation and end with a durable completion sentinel. If a journal already exists, return `EXECUTION_RECONCILIATION_REQUIRED`; do not relaunch. Reconcile live state first.
- Final acceptance must reference the exact accepted-unit manifest digest, which binds every accepted unit journal and the complete touched-record inventory, before changing `WIP` to `Draft` or updating `scan-state.json`.
- Persist action-specific rollback capsules before every original mutation and structured observed identities afterward. An unaccepted active execution and an accepted pre-finalization receipt are both rollback-capable across chats. A finalized session is not; create a corrective release instead.

## Explicit Interactive Gates

For any interactive chat review or approval, **MUST read** [references/bot-integration.md](references/bot-integration.md) and [references/bot-prompts.md](references/bot-prompts.md). Do not rely on a generic request such as “please approve” or show an unexpanded digest placeholder.

At every gate, report the phase, status, complete artifact paths, reviewed scope, blockers, and the exact digest that binds the decision. End with exactly one copy-ready approval line:

| Gate | Bound artifact | If approved, reply exactly |
|------|----------------|----------------------------|
| Grouping review | Complete candidate-proposal semantic digest | `APPROVE_GROUPING sha256:<proposal-digest>` |
| Write approval | `proposedExecutionBatch.batchDigest` | `APPROVE_WRITES sha256:<batch-digest>` |
| Document review | Active unit ID and its `executionJournalDigest` | `APPROVE_DOCUMENT <review-unit-id> sha256:<execution-journal-digest>` |
| Rollback approval | Active or accepted unit ID and its deterministic rollback manifest | `APPROVE_ROLLBACK <review-unit-id> sha256:<rollback-manifest-digest>` |
| Acceptance review | Complete accepted-unit manifest and touched-record inventory | `APPROVE_ACCEPTANCE sha256:<acceptance-manifest-digest>` |

Replace every placeholder with the current full ID and digest before asking. Bare approval words, a digest without its gate command, conversational approval, or a stale digest is not approval. If any bound artifact changes, regenerate the digest and request approval again. In verified batch mode, one WRITE or DOCUMENT_REVIEW reply binds the whole batch as defined in the shared contract; per-unit digests are still generated, validated, journaled, and reported — the human gate moves to the batch, never below the deterministic verification.

A multi-line batch reply is parsed by CODE, never by the executor. When a DOCUMENT_REVIEW (or other multi-unit) reply arrives, relay it verbatim — save the operator's text to a file or pipe stdin — into `bin/sdk-review-session.js resolve-batch-review --session <file> --reply <file|-> --gate-manifest <gate-manifest.json> --base-token <token>` (`--dry-run` previews; `--json` reports). The resolver classifies each `APPROVE_DOCUMENT <unit> sha256:<digest>` / `REQUEST_DOCUMENT <unit> <reason>` line, binds every line to the session's own pending journal by exact digest, derives touchedRecords from the journal, binds page/record links from the gate manifest, and applies — refusing the WHOLE reply before any state change on any line it cannot parse or bind (`REPLY_NOT_FULLY_PARSED`, `REPLY_DIGEST_MISMATCH`, `REPLY_UNIT_NOT_PENDING`, `REPLY_LINKS_MISSING`). Never decide per-unit accept/request yourself, summarize, or re-order a multi-line reply: an executor that re-classified nineteen executed `APPROVE_DOCUMENT` lines as change requests (2026-10-07 R16) left executions intact while their receipts never landed — that judgment call is no longer yours to make. A unit the reply does not address stays pending and is never accepted by default.

Gate cards are plain text: interactive cards render markdown links AND bare URLs as unclickable text, so a gate card never carries live links. Before every gate ask — and for batch completion reports — run `scripts/gate-presentation.js`: `--from-dryrun <dry-run.json>` presents a write approval's page previews and record links, `--manifest <manifest.json>` presents any other gate's materials (live pages, records, session file, worklist). The script writes the numbered local materials index (`tmp/api-reference-sync/gate-presentation/latest.html`), auto-opens it (the single URL itself when there is exactly one link), and copies the primary target to the clipboard as the fallback; the gate card then carries only the digest, the unit list, and the index path, taken from the script's emitted card snippet — which contains no URLs by construction (a leaked URL fails the run with GATE_CARD_LINK_LEAK).

Approval and receipt digests are read ONLY programmatically and in full — from the session, the store, or the artifact file. A digest shown truncated in any display (chat card, log line, summary) is presentation, never input: it must never be typed back into a command or embedded in a receipt. Re-derive from the source instead; a pasted-together digest from displayed fragments is a fabricated approval.

Generate a grouping or other JSON review digest with:

```bash
node .claude/skills/api-reference-sync/scripts/review-artifact-digest.js <artifact.json>
```

## Domain Workflow

1. Release scope: read `scan-state.json`, then inspect both Git log and Git diff between the last accepted tag and target tag before deciding the release range. All three evidence sources are mandatory; a reference table, remote tag listing, or full scanner run does not replace the approval-grade Git log/diff scope.
2. Candidate proposal: normalize raw symbols to user-facing documentation identities, resolve existing Bitable records and live Drive ancestry, and stop for grouping and successor-track review. The grouping-proposal artifact is assembled only by `scripts/build-grouping-proposal.js` (`--scope` + `--identity-map` + `--decisions`, optional `--snapshot`): it binds the upstream artifacts as lineage digests, embeds identity-coverage accounting, and refuses a partition that is not exactly the scope's action set; after the operator replies `APPROVE_GROUPING`, the approval becomes durable only through `scripts/record-grouping-approval.js --proposal <file>` and binds into the campaign session — bin/sdk-doc-sync.js `--grouping-approval <receipt>` at session creation, or `sdk-review-session.js approve-grouping --session <file> --proposal <file>` on an existing session — after which every entry chains its `--release-scope` digest against the approved scope (GROUPING_STALE otherwise). Hand-assembled proposals do not carry lineage and cannot receive a receipt. The successor-track review is a same-pass source-track check: when a page's content derives from another track (the reverse-inheritance class), the SOURCE track's page is checked and reported in the same pass — fixing a derived page without checking the page it derives from is exactly how the v3.0 compact defect spread across tracks while each track's fix looked locally correct.
3. Reviewed planning: build source-verified artifacts and immutable plans; require `planCount == diffCount`, zero planning errors, known placement, and exact create/update evidence before requesting approval. Before a campaign starts, run `scripts/intake-preflight.js --strict --contexts <reviewed-context.json> --language <track>` over the materialized reviewed context (the workflow's intake hard step) — and when materializing contexts, any use of an in-KB page as a style template MUST be declared in that entry's `styleMirrors` key (web-content semantic references are exempt); undeclared mirroring bypasses the style-mirror allowlist gate, whose judgment only covers what is declared.
4. Collaborative execution: order the `reviewUnitManifest` deterministically, persist the session, select one document unit, approve and execute its complete Docx/Drive/Bitable action batch, verify it, then stop for digest-bound document review. Convert approval into a journal-derived receipt with `sdk-review-session.js`; accept the unit, apply comments, or plan a separately approved full rollback for that same unit. A changes-requested redo routes through REBUILD: re-planning that unit must supply UPDATE-grade evidence (verified placement, inheritance evidence) because the redo reuses the campaign's record and document — a CREATE-grade context alone fails closed at the REBUILD shape gates. A later chat resumes from that session file and never from a hand-written accepted-ID list.
5. Acceptance Finalization: after every planned unit has its own accepted journal receipt, build and persist the complete accepted-unit manifest. After the user separately approves it, change every touched interface-document record from `WIP` to `Draft`, refetch and verify, then update `scan-state.json`. Record finalization in the session only from the successful acceptance journal. Structural VirtualNode or Module records stay outside this transition. Partial unit acceptance never advances the baseline. A campaign closes only when its accounts are clean: every session it created is terminal (no in-progress units, no pending executions) and scan-state has advanced past the session's releases — a session still marked in_progress after its campaign closed is a zombie the start-of-session dashboard flags red, not a resumable state. The close runs the process-learning capture (打回即铸): `sdk-review-session.js list-learning-events` lists every learning event the close must account for, `record-learning-suppression --session <file> --event-key <key> --rationale <text>` records the explicit not-a-rule rationale for one event, and `close-session` itself writes one rule-candidate draft per uncaptured event into `tmp/skill-feedback/api-reference-sync/candidates/` before the session may close — a reviewer's rejection never leaves the session without a trace.
6. Campaign-runner launch preflight: a new campaign workflow script ships only after the checklist passes — EXECUTE treats PARTIAL as failure (through the shared `interpretExecutionOutcome` helper: PARTIAL mutated live state, so record the unit, stop the campaign, reconcile the journal — never blind-retry); VERIFY reads the fields the session actually persists; the harvest/acceptance step checks the review answer's shape before accepting anything (missing decision stops the run; a unit the answer omitted is never accepted by default); receipts carry `--base-token`; workflow args have hardcoded fallbacks plus a first-line args-completeness canary that fails loudly. And the script is COPIED FROM THE CERTIFIED TEMPLATE — never inherited from a sibling campaign script (the v30 template's latent PARTIAL misreading was inherited by v26 exactly that way; the certified template is the java v2.6.x runner with the v2 intake).

## Domain Invariants

- Layout rules (global, all languages): a method with a single request type never gets its own H3 subsection — the builders/parameters sit directly under the page-level request section as BUILDER METHODS/PARAMETERS; H3 variant headings exist only to separate multiple request types. The Example section is a bare code block with no per-example H3; example descriptions stay as plain text. [api.global-layout-rules]
- Classify ownership as `standalone`, `method_owned`, or `ambiguous`. Embed method-owned request, response, result, task, info, iterator, descriptor, transport, and wrapper types in their public owner pages. [api.ownership-classification]
- A public class is not standalone evidence. Ambiguous ownership blocks planning; standalone creation requires an explicit reviewed standalone exception. [api.standalone-evidence-gate]
- Preserve one document per established public interface record. Parameter-only changes update every affected owner page; they do not justify a synthetic umbrella page. [api.one-document-per-interface]
- Treat release folders as sparse version-local deltas and version Bitables as complete indexes. Unchanged entries may retain inherited links. [api.sparse-version-delta-model]
- Versioned Drive trees follow the delta model (global, all languages): the older track's tree (e.g. `v2.6.x`) holds the full page inventory, while the newer track's tree (e.g. `v3.0.x`) holds only the pages whose content changed relative to the older track. Unchanged interfaces keep one shared document in the older tree and both tracks' records point at it. When an updated interface's category directory does not exist in the newer tree, create it as a sibling under the newer tree root before copying, and repoint the newer track's category VirtualNode to the new directory. In the source track's own sync, a shared cross-track document may be patched in place only when every other record referencing it carries an inheritance-review classification that accepts the change (`no_successor_action`); any unclassified, deferred, excluded, or action-requiring referencing record forbids the in-place patch. When a review rules that a still-pointing successor track must not receive the change, first create the successor-side copy inside the successor track's own tree and repoint the successor record to it — approved and executed in the same batch before the in-place patch, so the copy preserves the pre-patch content — and only then patch the shared document from refreshed post-repoint evidence. When a successor track has already forked its own same-name document, the source track's change reaches that document only through an explicit successor action in the same batch; successor inheritance is never broken by silently forking the shared document. The executed transition follows a fixed DAG — create the category folder, then copy-patch and repoint the interface record, and only after the copied document is verified repoint the category VirtualNode as a distinct downstream action — and ends with a post-write tree-delta verification that refetches both tracks before acceptance. [api.versioned-tree-delta]
- Treat Bitable navigation type, `Docs` resource type, and physical Drive placement as separate facts. A `Class` record may point to a Docx landing page and still parent method records; the record does not become a `VirtualNode`, even when the language profile requires the landing page and method pages to live in a same-named Drive folder. [api.placement-facts-separate]
- For a canonical stateful-class identity, require the versioned organization profile from the identity map, a reviewed `organizations[]` contract with the complete public-method inventory, and an explicit `target.releasePlacement`. The reviewed-context builder and planner must reject a category-folder target, a class VirtualNode, a non-Docx class link, an incomplete child inventory, or child records not parented to the Class. [api.stateful-class-identity]
- Bind every reviewed stateful-class contract to the scanner-derived `organizationInventory`, including its stable digest. The planner must validate that inventory again instead of trusting a caller-provided `complete: true` declaration. [api.organization-inventory-binding]
- For a changed inherited interface, use `COPY_PATCH_AND_REPOINT`: copy into the current release folder, patch the copy, and repoint the current record. [api.changed-inherited-copy-patch]
- For an unchanged inherited interface whose `Docs` token is already correct but whose `父记录` or `Type` is stale, use `UPDATE_RECORD_METADATA`: preserve the document token and revision, perform no Docx copy or patch, and verify the record link, parent, record type, and `docx` resource type. [api.unchanged-inherited-metadata-update]
- Resolve the canonical target folder and parent from current hierarchy evidence. Unknown current version, folder, or shared-token state blocks planning. [api.current-hierarchy-resolution]
- Keep a small tracked evidence manifest for every organization rule used by planning. It must record exact Base/table and Drive identities, representative record parent/type/link facts, Docx revisions and content hashes, collection identity and time, and copy-ready read-only replay commands. Do not substitute an untracked scan dump or a self-declared candidate contract. [api.organization-evidence-manifest]
- SDK artifacts require reviewed evidence, a versioned language layout profile, block-safety validation, and an immutable semantic patch plan. Full-body repair requires exact token approval, history, and protected-block inventory. [api.reviewed-artifact-evidence]
- Verify the canonical tenant host, target ancestry, record link/parent/metadata, older-source preservation, and human-visible access after writes. [api.post-write-verification]
- A grouping approval binds the campaign to the exact release scope it covers: the operator's APPROVE_GROUPING lands durably through `scripts/record-grouping-approval.js` and binds into the campaign session (bin/sdk-doc-sync.js `--grouping-approval` at session creation, or `sdk-review-session.js approve-grouping` on an existing session — one-shot, a different proposal refuses GROUPING_APPROVAL_ALREADY_BOUND); once bound, every dry-run, resume, or live write must present a `--release-scope` whose semantic digest is the approved proposal's lineage scopeDigest — a re-scoped, hand-swapped, or missing scope refuses typed (GROUPING_STALE / GROUPING_APPROVAL_CHAIN_INVALID), so any newer candidate spec, reviewed context, scoped dry-run, or execution artifact requires a fresh grouping gate. [api.grouping-proposal-staleness]
- A candidate grouping proposal is a governed gate artifact, never a hand-assembled one: it is built only by `scripts/build-grouping-proposal.js`, which binds the release scope, identity map, and (when present) the Bitable snapshot as semantic digests in `lineage`, embeds identity-coverage accounting, and refuses a non-approval-grade scope, an ambiguous-ownership action, or a units/exclusions partition that is not exactly the scope's action set (every action grouped or explicitly excluded, none foreign, none twice); the operator's APPROVE_GROUPING becomes a durable credential only through `scripts/record-grouping-approval.js`, which writes a digest-keyed receipt, refuses a proposal that fails schema validation, and cross-checks the lineage digests against the upstream artifacts when they are passed (`--scope` + `--identity-map`, the recommended issuance form) — and a scout over a track whose identity map is missing or malformed fails with a typed blocker (SCOUT_IDENTITY_MAP_MISSING/INVALID, with the identity-reconcile draft workflow as recovery) instead of a raw crash. [api.grouping-proposal-governance]
- Convert governed markdown into Feishu blocks without silent loss: the converter refuses any markdown token it cannot represent instead of dropping it, renders pipe tables as native table blocks with plain-text cells, and declares the cell refetch fixed points (authored `\_` escapes consumed at write; end-of-cell `<br>` stripped only by verification normalization). [api.markdown-block-fidelity]
- Keep repository-relative URLs out of written documents: reviewed-context builders resolve repo-relative `.md` links to in-KB docx URLs from reviewed snapshot evidence (or explicitly de-link unresolved ones), and the writer envelope refuses any text link that does not decode to an absolute http(s) URL before the first writer call. [api.absolute-link-urls]
- Never route a page carrying user-authored `<include target="...">` conditional markers through a body rebuild: the artifact provider refuses a verbatim rebuild artifact whose content contains include markers and the executor refuses a rebuild patch over such content (INCLUDE_REBUILD_FORBIDDEN); surgical child-block insertion is the only sanctioned edit path for these pages. [api.literal-include-preserved]
- Reserve the Bitable Description field for VirtualNode (Drive folder) records: governed record writes refuse a non-empty description on any record that is not a VirtualNode (DESCRIPTION_SCOPE_VIOLATION), re-reading the record's live type when the payload does not carry it, and executor update paths never pass a description for interface records. [api.record-description-scope]
- Prove verbatim pages landed intact: a merged-PR page's normalized content digest is attested into the approved plan, in-place patch strategies refuse cross-type block pairings and demand a rebuild when shapes diverge (REBUILD_REQUIRED_SHAPE_MISMATCH), and execution completes only after the refetched raw_content compares line-for-line against the attested content through the declared canonicalization, with the outcome persisted in the journal and acceptance receipt. [api.pr-verbatim-content]
- Post-verbatim polish is a governed per-unit phase, never a verbatim bypass: a merged-PR page may be polished only after its verbatim landing carries a passing content-fidelity journal outcome and before that unit's document review closes. Prose polish edits arrive as a subagent-proposed manifest anchored to unique substrings of the verified content, never touch fenced code, inline code spans, table rows, headings, include marker lines, metadata footers, or add, drop, or reorder an absolute link URL, and refuse whole-body rewrites. Restructure polish (format unification per the 2026-10-01 semantic ruling) arrives as a replacement-content manifest whose canonical content must preserve every upstream structural item — parameter and builder items, fenced code blocks, the declared return type, exception items, tables, include markers — through the semantic content map, may never add, alter, or drop a code block, and must cite the SDK source (path and lines bound to the table header) for every introduced response-shape table; description wording is never machine-compared and stays with the polish proposal and human review. In either mode the refetched page must compare line-for-line against the deterministically recomputed polished content through the same declared canonicalization, with base-content, manifest, and terminal digests recorded so acceptance and reconciliation bind the polished terminal state. [api.pr-polish-governed]
- Keep the governed document inventory closed: every document under a tracked release folder is either a record's Docs target or referenced by a percent-decoded page block link; reconciliation reports unreferenced documents, callout blocks carrying auto-populated empty children, and reviewed contexts whose frozen digest or live raw_content disagrees with their content — as detect-only findings that never authorize disposal. [api.governed-document-inventory]
- Write pages that conform to their language's declared layout profile: per-language layout rules live only as versioned data in the renderer layout profiles (never duplicated in enforcement code), one language-neutral checker evaluates the declared structural rules — builder signature prefixes, single-request H3, example H3, deprecation callout shape, and where a profile declares them split RETURN TYPE/RETURNS sections with RETURNS prose and no duplicated type row — and, since the 2026-10-03 global ruling, the five byte-judgeable content rules that every track declares through the global base: no CJK characters anywhere in page text (CONTENT_CJK_MIXING), the page body's first sentence matches a declared register pattern ("This operation …" for operation and getter pages, "A Xxx instance is …" for class/type pages, per the 2026-10-04 adjudication) (FIRST_SENTENCE_REGISTER), any rendered RETURNS section carries a response-fields PARAMETERS bullet list in the strong describeReplicas form, with error-only returns listed as their response field (RETURNS_MIN_DEPTH), every bold-name parameter bullet carries a non-empty description (PARAM_DESC_REQUIRED), and Notes lines exist only inside governed callouts, never as bare page lines (INTERNAL_NOTE_LEAK); all are enforced at the operational verify step and over live pages in reconciliation, open-ended wording quality stays with the governed polish phase and model evals, and rules a language does not declare still do not apply to it. [api.sdk-page-layout]
- Treat same-title sibling documents as cross-track copy-patch structure, never as duplicates: classify every same-title set language-wide by pointing rows and Drive containment — a copy referenced by any track's record `Docs` link or a page block link is protected lineage that no dedup, merge, or cleanup may touch and must sit under its claiming track's release root per the delta model (the newer track's copy of a changed interface belongs in the newer track's tree, not beside the older copy), a copy with zero pointing rows is the only true orphan candidate and disposal requires explicit operator approval, and one track's records pointing at multiple same-title copies under one parent is a re-point defect. [api.same-name-sibling-placement]
- Guard every governed Drive/docx write with the reconcile discipline: a folder create refuses a same-named FOLDER sibling in the parent directory outright, whatever the caller (FOLDER_NAME_COLLISION — same-name folders in one directory are always a defect, the duplicate-directory class); every duplicate-prone mutation (folder create, document create, copy, rename) reads back its expected post-state after applying and refuses on mismatch (FOLDER_CREATE_POSTCHECK_FAILED / WRITE_POSTCHECK_FAILED); and a write whose response is lost is never blind-retried — the writer reconciles against live state by name or title and adopts only what the read-back proves, surfacing reconciledAfterFailure for the journal (the duplicate empty-directory incident class). deleteFile is exempt by policy: a retried delete that already landed fails loudly as not-found rather than doubling a side effect, and absence cannot be proven without the parent folder. [api.write-boundary-reconcile]
- Bind every placement decision to the live walk it derives from: the placement audit product carries a walkDigest (the machine fingerprint of its entries), candidate specs must carry it (placementWalk — PLACEMENT_WALK_REQUIRED otherwise), the planner binds it into every plan (placementWalkDigest), and a live execution names the walk it is bound to (--placement-walk-digest, from the session's placementWalk) — plans deriving from a different walk, several walks at once, or an unbound execution carrying walk-bound plans are refused before any write (PLACEMENT_SOURCE_STALE / PLACEMENT_WALK_DIVERGENT / PLACEMENT_WALK_UNBOUND); and a CREATE's planned target folder must be live-resolvable under the target version root at the write boundary (PLACEMENT_TARGET_UNRESOLVED — the audit-side "target = the sibling pages' measured folder" check, enforced pre-write). [api.placement-live-binding]
- Treat content-level teardown-and-redo as a first-class REBUILD, never as a second CREATE (the J6 class: a changes-requested redo used to die on CREATE_RECORD_ALREADY_EXISTS or silently double-create): a CREATE-like action whose record already exists auto-routes to REBUILD when the session's execution history proves the record is this campaign's own product, and an explicit REBUILD over any other record fails closed as an operator adjudication (REBUILD_SCOPE_FOREIGN). A REBUILD reuses the campaign's recordId and documentToken — postconditions pin both, no new ids are minted — lands whole-body replacement bytes through the governed rebuild patch strategy (a surgical apiPatchPlan artifact is the UPDATE path and is refused at plan and at the write boundary — REBUILD_STRATEGY_REQUIRED), rides the same versioned-tree attestation and shared-token classified shape as an in-place patch (whole-body replacement affects every referencing track just the same), and binds the newest prior execution journal digest from the session's change-requests as metadata.rebuildOf so the receipt lineage never breaks (REBUILD_SOURCE_REQUIRED / REBUILD_PLACEMENT_REQUIRED / REBUILD_TREE_DELTA_INVALID / REBUILD_LINEAGE_DIGEST_INVALID on the respective shape failures). [api.rebuild-first-class]
- Classify track topology against the fallback-chain model as the release fetch actually assembles it (2026-10-04 operator adjudication): each language's registry track order is the fallback chain, a section folder sits under the owning tree or a recorded fallback source (else TOPOLOGY_SECTION_FOLDER_FOREIGN/UNRESOLVED), page-level fallback is the DESIGNED form — a page document living in an older tree while its section points at the own-tree folder is never a defect, and file-anchor families (anchored by a same-directory document rather than a folder-recorded section) are sanctioned, so unclaimed slugs surface as TOPOLOGY_PAGE_SECTION_UNKNOWN info; the real error classes are record Slug fields carrying pasted URLs instead of the plain section name (TOPOLOGY_RECORD_SLUG_URL — the form is text=<section name> with the link in Docs), page documents sitting under a NEWER track's tree (TOPOLOGY_PAGE_OUTSIDE_SECTION forward cross), documents under no walked root (TOPOLOGY_PAGE_UNRESOLVED), and a document sitting beside a same-named folder in one directory (TOPOLOGY_SAME_NAME_SIBLING — the stray-duplicate form, scanned under the config's sameNameInOneDirectory policy, with operator-recorded token exemptions surfaced as TOPOLOGY_SAME_NAME_EXEMPTED info) — detect-only findings, machine-enforced at the reconcile stage by reconcile-content.js (error findings gate --strict) and walked by scripts/audit-track-topology.js as the intake preflight that blocks campaign planning until each item is fixed through the decision table in config/fallback-topology.json or explicitly exempted, where the table is load-bearing rather than documentation: the classifier refuses to run without its record-points-at-recorded-fallback-source → NONE row (the grantPrivilege precedent) and its sameNameInOneDirectory policy; and because the Slug column is a formula over the Docs display text, every record write path (governed writers and repair tools alike) writes the Docs cell as {text: <section name>, link} and verifies the reread display text — a bare-URL string poisons the whole family's slugs (2026-10-04 campaign-defect class, machine-gated as TOPOLOGY_RECORD_SLUG_URL). [api.track-topology-audit]
- Mirror page style only from operator-designated exemplar pages: a reviewed-context entry that uses an in-KB page as a style template must declare it in styleMirrors, and every declared source must sit in that language's allowlist in config/style-mirror-allowlist.json — intake preflight refuses a non-listed source (STYLE_MIRROR_SOURCE_NOT_ALLOWLISTED) and a malformed declaration (STYLE_MIRROR_ENTRY_INVALID), and an unreadable or malformed allowlist aborts the run before any entry is judged (STYLE_MIRROR_ALLOWLIST_MALFORMED, fail closed). An accepted page is not a correct template by default (the v3.0 compact defect spread into v2.6 exactly through mirroring accepted-but-defective pages): web-content stays the semantic reference source whose completeness the semantic content map governs, the designated exemplars are the only style-template source, and adding a page to a language's allowlist is an operator decision recorded with its rationale in the same config. [api.style-mirror-allowlist]
- Close a two-gate session only with its process learnings on the record (打回即铸): every change request and every changes_requested or rejected decision the session accumulated is mechanically converted into a rule-candidate draft under `tmp/skill-feedback/api-reference-sync/candidates/` at close time, or explicitly suppressed with a recorded rationale — closing without a capture report fails closed (PROCESS_LEARNING_CAPTURE_REQUIRED), a capture that cannot persist a candidate blocks the close (PROCESS_LEARNING_CAPTURE_FAILED), and the closed session stamps the captured candidate ids and suppressed event keys so no operator rejection can evaporate silently. [api.process-learning-capture]
