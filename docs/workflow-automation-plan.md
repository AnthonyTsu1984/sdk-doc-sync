## 0. 一句话结论

看板（dashboard）批 1–10 已经把控制平面建出了八成——发现（哨兵卡+发现呈门）、状态（战役卡/三门/回执/多检出）、执行面（spawn worker+界面批准转发）、遥测（token 逐篇归因）都在；**缺的不是展示，是链条与调度：环节之间仍靠人盯、人点、人想起**。本规划把"每个环节的间隙"自动化，人只留在门上。终态不是"无人"，而是**全自动流水线 + 人只处理异常队列**。

## 1. 目标与"三种自动"的区分

规划前先拆词，避免三个不同难度的问题混在一个口号里：

| 名称 | 含义 | 判定 |
|---|---|---|
| **全自动执行** | 扫描→提案→写入→验证→关账一路跑完，无人在场 | 技术可达，主线（§4–§6） |
| **全自动批准** | 机器自己签自己的写门 | 可达但有前提（§5 L1 信封 + 信任根） |
| **全自动判断** | 新类型缺陷、新政策裁定也无人 | **不追求**——这不是技术缺口，是 campaign-control-hardening §0 刻意保留的人工注意力位置（"人工注意力只花在新类型的缺陷上"） |

## 2. 已具备的底座（为什么比看起来近）

最难自动化的部分恰好已经做完：

1. **验证层零模型化**：digest / journal / refetch 对账 / 回放全是纯脚本，不依赖模型自证——无人值守的安全前提。
2. **执行可回放、可归因**：batch digest 绑定 + one-shot journal + 回滚机制（6.7 fault-injection、6.8 release-gate），影响有界、可倒放。
3. **探测与批准已批量化**：两门模型压掉了总验收；#119 resolve-batch-review 已是"执行者转发、决策者批决"——机器签发批准的雏形；信封执行开关（`--approve-batch-digest --auto-approve`）已存在。
4. **打回即铸闭环在跑**（批 7，3456bea）：close-session 硬校验 + runtime 拒绝入 violation ledger + 学习事件自动转 rule-candidate——"什么时候可以扩大自动面"从此有实证账本，不靠感觉。
5. **控制平面**：看板六级下钻、统一决策队列（"待你决定"置顶）、/attach 确定性简报（上下文格子化雏形）、spawn→停门→UI 批准转发全链、多检出感知、token 逐篇归因、轨键治理收口（#122/#124：registry 显式键 + 印章>registry>推导解析序 + host registry 单一消费源）。
6. **哨兵自动化**：三条 cron 只读扫描（cpp 09:00 / go 09:15 / java 09:30），事件流天然进看板。
7. **hooks 阶段 A**：SessionStart 治理看板注入在运行（用户级注册）。

已知债务（S0 消化项）：java 修订战役双行 wart；hooks 阶段 B–D 未施（L0 旁路仅 prose 禁止）；rule-promotion 消费端未启动（rule-candidate 会堆积）；go/java 战役分支 harness 提交未回主线（S4 通道）。

## 4. 分阶段改造（每级独立可验收，爆炸半径逐级放大）

### S0 地基修缮
修 java 双行 wart（会话卡↔修订卡互重去重、`groupingApproval=null` 判批）；server 启动打 commit 版本戳（看板版本不匹配即黄牌，替代"人记得重启"）；卡片增加**门停留时长**（gate dwell）——后续 SLA/通知的供数。
验收：双行消失；重启后卡片一致；dwell 可测。

### S1 决策收口：统一队列 + 主动通知（注意力回路闭合）
总览"待你决定"升级为跨战役统一决策队列（门类型/已等待时长/爆炸半径/主按钮=一键批准，链路复用批 4/5）；接**飞书 bot 通知**（事件=门材料就绪、typed blocker 入队、哨兵 stale、awaiting-close、zombie——只告可行动项）；新增 09:45 汇总 cron（三轨扫描结论+队列快照+昨日指标）。
验收：操作员从"盯板"变"收通知"，每天集中处理两窗即可。

### S2 编排器：门间自动推进（人在门上，不在环节间）
现状"批准→worker 续跑到下一门"已通，缺门与门之间的自动派单。交付：① saved workflow 骨架泛化（java 三份 .dwf.ts 抽成参数化模板，go 剩余单元直接骑上——最大受益者）；② hooks 阶段 B/C 先行（deny 表+R6 准入门），无人值守的护栏前提；③ 格子化执行按 §6。
验收：go 剩余单元按批跑，操作员每批触点 ≤2 次（分组+写门），单格上下文与战役长度无关。

### S3 自动面扩大：信封执行 + 错误预算（把人从重复决定中撤出）
**信封政策引擎**：预批准类别写成数据（纯新增/非共享 token/无删除/五条规则绿/semantic-content-map 过）→ 命中即自动签发 APPROVE 行（digest 绑定不变；政策文件本身过 admission+评审+statementDigest）。**错误预算执法**：rule-promotion 消费端启动，"连续 N 战役零 P1 且 ledger 无新增 code"=类别晋升条件，打回超预算自动收缩回人工门。信封类先过影子空间 canary 再进生产空间。看板加 DORA 面板。
验收：低风险类自动通过率可观、打回率不升。

### S4 稳态：回主树流水线化 + 并发调度
回主树三通道入流水线（跨轨修复 cherry-pick 快车道 / 战役收口整批 PR / 长分支按主题分波——go 轨分支膨胀的解法）；三轨并发编排（同轨串行写、admission 跨轨串行化）；**删除/共享档 in-place/REBUILD 永久人工门**写入红线。
验收：战役收口的"打包送审"不再依赖人想起；三轨并发不互踩。

## 5. 全自动分级（S3 的内部刻度）

- **L1 预批准类别**（最先做）：类比 Terraform auto-apply on trusted plans / GitHub auto-merge on green。信封外的一切照旧走人工门。
- **L2 异常队列战役**：整条流水线无人值守，typed blocker/新类型缺陷即停入队等人；人从"每批批准者"变"异常处理者"。
- **L3 稳态运行+爆炸半径分级**：新增/修改走全自动，**删除/重建/共享档 in-place 永远双人规则或人工门**（update_document 清页事故前科）。

两个诚实天花板：
1. **信任根要换**：回执无签名，单操作员威胁模型是"防漂移不防伪造"；机器签门时即自我循环。真要紧场景（删除类、大批量）加签名或双签；审计靠 ledger+看板事后追查兜底。
2. **语义保真长尾**：结构化"内容不能少"已有 semantic-content-map 机器门，但"内容对不对"上限归 eval 和人。全自动后这类问题从"门上拦"变"队列里等"——异常队列消化速度（rule-promotion 跑起来）成为新瓶颈。

## 6. 上下文管理架构（无人值守的前提）

原则：**上下文窗口是可丢弃的工人，session 文件+journal+scan-state 是账本；格子之间交接的永远是盘上工件，永远不是对话记忆。**（现行 42% 换对话轮换协议的人工预演——轮换能活恰因战役状态从不在对话里。）

四个机制：
1. **控制流外置**：脚本是不衰减的"长上下文"（java 战役后期控制流搬进 .dwf.ts 后探索骤降、117/117 收口即实证）。
2. **格子化**：每格新 subagent + 薄自足 prompt（session 路径+单元 digest+skill 路径+门禁速查），上下文长度按设计封顶、与战役总长无关。
3. **幂等断点**：格子中途耗尽/漂移→fail-closed 停（typed blocker 拦、journal 记账）→编排器杀掉重开新格重放；journal 幂等（DUPLICATE_COMPLETION_SENTINEL 去重）保证重开只重付未落盘的几步。**绝不抢救长上下文**——判断"还能不能信"本身不可靠，只按"落盘到哪了"重放。
4. **编排器无记忆**：cron/工作流链每次点火自带完整自足 prompt（三条哨兵已是此形态）；typed session reader（批 6）让新格确定性接管。"换会话"从 42% 启发式变每批/每单元一次的确定性动作。

验证层天然免疫：digest/refetch/对账纯脚本，验证第 N 个单元从不需要写作时的上下文。
反面铁律：**不要让系统学会"写交接总结然后接着干"**——那是最不可靠的部件自证可靠性。交接只认盘上工件，摘要只由机器从 journal 生成；模型记得什么不重要，落盘了什么才重要。

## 7. 红线（继承 + 新增）

继承：看板无写路径、不造第二真相、写只在 canonical CLI、digest 绑定由 L1 执法、scan-state 只由 close-session/finalize 推进。
新增：编排器只 spawn/relay 不写；信封政策数据本身是受治工件（admission+评审+statementDigest）；破坏性动作与共享档变更恒人工双人；自动批准必须留痕进 violation/journal 台账；hook 在位后直调即拒（阶段 D 收尾时入 Golden Rules）。

## 8. 依赖与落地顺序

- **依赖图**：S0 无前置；S1 依赖 S0 的 dwell 供数；S2 依赖 hooks B/C 与 workflow 骨架；S3 依赖 S2 骨架 + 打回即铸 ledger 数据 + rule-promotion 消费端；S4 与 S2 可并行（分支积压不该再等）。
- **三轨现状即梯队**：py 已收口（S4 通道走完，#120 落主线）；java 修订在跑（骑 S1）；go 剩余单元最多（S2/S3 主试点场）。
- **若只做一件**：S2-①（go 轨换 saved workflow 骨架）——直接对着当前最大耗时项。

## 9. 度量（怎么算成功）

| 指标 | 口径 | 数据源 |
|---|---|---|
| 单元 lead time | 发现工件→单元 accepted | session 文件+journal 时间戳 |
| 门 dwell | 门材料在位→批准行落盘 | S0 新增字段 |
| 操作员触点/批 | 门禁往返次数 | /api/approve 日志+回执 |
| 自动通过率 | 信封类放行/信封类总数 | S3 信封引擎台账 |
| 打回率（错误预算） | P1/changes-requested 次数/单元 | violation ledger + 打回即铸 |
| 异常队列时延 | 入队→处置完成 | S1 队列事件 |
| token 结构 | 写作格占比（目标六到八成） | 批 7 sqlite 逐篇归因 |
